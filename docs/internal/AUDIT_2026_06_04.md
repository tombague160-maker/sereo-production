# Audit ultra-complet Sereo — 2026-06-04

## Verdict global

L'application Sereo (v1.17.1) presente une **base saine** sur les fondations critiques (recovery SQLite v1.16.0, rate-limiting auth, CSP stricte, backups gzip avec retention) mais souffre de **dette technique architecturale significative** sur trois axes : (1) **concurrence et integrite transactionnelle** — TOCTOU race entre readDb/writeDb, lost-updates possibles sur mutations simultanees, reservation stock non-liberee sur transitions terminales ; (2) **performance frontend O(n²)** — getNeededQuantityForProduct rescann 500×1000 commandes par render, normalizeDb sur chaque readDb, backup gzip synchrone bloquant l'event loop 100-500ms ; (3) **accessibilite et UX destructive** — window.confirm() pour purge/reset, focus management modal absent, contraste insuffisant en dark mode. **Aucun bloqueur P0 de production** — le systeme tourne et recupere correctement de la corruption — mais 24 P1 imposent un sprint de hardening avant croissance multi-utilisateur. Priorite suggeree : (1) verrou pessimiste readDb/writeDb, (2) backup async + checkpoint WAL, (3) liberation stock sur transitions probleme/reprogrammer, (4) modales accessibles pour confirmations destructives.

## P1 — Majors (sprint prochain)

### TOCTOU race condition entre readDb() et writeDb()
**File** : `server.js:1309-1343, 3749, 4126`
**Evidence** : Pattern `db = readDb(); [mutations]; writeDb(db)` sans verrou. Deux requetes concurrentes (POST /api/import/ventes + PATCH /api/stock/:id) lisent le meme snapshot puis ecrivent successivement : la 1re ecriture est perdue. SQLite BEGIN IMMEDIATE protege l'atomicite SQL mais pas l'isolation applicative.
**Impact** : Perte silencieuse de mutations en usage multi-onglet ou multi-utilisateur.
**Fix** : Verrou pessimiste — `readDb()` ouvre BEGIN IMMEDIATE, `writeDb()` commit. Alternative : Mutex `async-lock` autour de chaque couple read/write. Ajouter test concurrent `Promise.all([patch1, patch2])` qui valide pas de perte.

### Race condition reservation stock sur start-preparation concurrent
**File** : `server.js:4254-4272` (POST /api/orders/:id/start-preparation)
**Evidence** : `reserveStockForOrder(db, order)` apres `readDb()` sans verrou. Deux users X et Y cliquent en simultane : tous deux voient `stockReservedAt=null`, reservent 100 unites chacun, stock final = -100 au lieu de 0.
**Impact** : Stock physique negatif, sursollicitation, preparation en stock fantome.
**Fix** : Optimistic locking — ajouter `version` incremente sur chaque writeDb, retourner 409 Conflict si version stale. Ou envelopper readDb+analyzeOrderStock+reserveStockForOrder+writeDb dans BEGIN IMMEDIATE avec SELECT FOR UPDATE.

### Stock reserve jamais libere sur transitions probleme_livraison / a_reprogrammer
**File** : `server.js:2896-2912, 3165, 3170, 3173`
**Evidence** : `reserveStockForOrder()` deduit physiquement le stock (`setStockQuantity(product, available - line.required)`) et garde `stockReservedAt`. Transitions vers probleme_livraison/a_reprogrammer n'effectuent aucune liberation. Pire : `calculateReservedStock` (l.2371) exclut ces statuts du calcul reserve — stock physiquement deduit mais invisible des metriques.
**Impact** : Trou comptable invisible. CMD-001 avec 40 unites de produit X bascule en a_reprogrammer = 40 unites perdues du systeme.
**Fix** : Creer `releaseOrderStockReservation(db, order)` appelee AVANT setOrderStatus dans les transitions terminales non-livre. Modifier `reserveStockForOrder(db, order, force=true)` pour permettre re-reservation a la reprise.

### backupDbIfNeeded synchrone bloque event loop 100-500ms
**File** : `server.js:1820-1822` (zlib.gzipSync + fs.readFileSync + fs.writeFileSync)
**Evidence** : Appele dans `writeDb()` apres chaque mutation. Sur DB 50-100MB, compression gzip synchrone bloque tous les handlers HTTP 200-500ms. Le throttle 1h ne supprime pas le blocage, il l'ajourne.
**Impact** : Latence percue 100-500ms sur 22 endpoints critiques (imports, CRUD).
**Fix** : `setImmediate(() => backupDbIfNeeded())` apres `writeDb()`. Migrer vers `zlib.createGzip()` stream ou `worker_threads`. Catcher erreurs silencieusement.

### getNeededQuantityForProduct O(n²) — 5 secondes lag sur renderRecommande
**File** : `public/js/app.js:3693-3709`
**Evidence** : `orders.reduce(...products.reduce(...))` appele par produit dans `renderRecommande` (l.1242). 500 produits × 1000 commandes × 20 produits/commande × 6 normalizeTextKey = ~60M ops par render. Pas de cache.
**Impact** : renderRecommande tab freeze 5+ secondes a chaque loadData ou filter change.
**Fix** : Backend pre-calcule `quantityNeeded` par produit dans `/api/stock`. Frontend hit cache via `order.quantityNeeded ?? fallback`. Alternative : Map<productCode, neededQty> construite en O(orders × items) puis lookup O(1).

### calculateReservedStock + calculateNeededStock recalcules par produit
**File** : `server.js:2367-2386, 2398-2526`
**Evidence** : `enrichStockItem` execute 3 appels (calculateReservedStock × 2 + calculateNeededStock × 1) par produit. `getStockView` × 100 produits × 100 commandes × 5 items = 250k iterations par GET /api/stock. `getDashboardSummary` re-execute getStockView puis applique 20 .filter() supplementaires.
**Impact** : 50-150ms par GET /api/stock et /api/dashboard sur 100+ commandes.
**Fix** : Pre-computer `Map<productId, {reserved, needed}>` une fois par requete via une passe sur commandes. Refactor getDashboardSummary en single-pass aggregation.

### normalizeDb appele sur chaque readDb (10-30ms gaspilles)
**File** : `server.js:1567-1589`
**Evidence** : 8 `Array.isArray()` no-op sur chemin SQLite + `ensureOrderNumbers` scan filter + `normalizeSettings`. Le commentaire v1.14.0 documente le retrait de syncWorkflow mais le reste persiste sur chaque GET.
**Impact** : 10-30ms par GET pour valider donnees deja valides.
**Fix** : Creer `normalizeDbForJsonPath()` distincte. Sur chemin SQLite, normalizeDb devient quasi no-op. Ne pas cacher l'objet db (risque stale state).

### ensureOrderNumbers O(N×M) — 500ms boot sur 5000 commandes
**File** : `server.js:1620-1651, 2559-2588`
**Evidence** : `generateOrderNumber` scanne `db.commandes.map().filter()` puis boucle regex sur existingNumeros pour CHAQUE numero manquant. 5000 commandes × 100 missing = 500k iterations sur DB legacy.
**Impact** : Boot spike 500ms+ en mode JSON ou apres migration v1.9.0.
**Fix** : Precomputer `maxSeqByYear` ONCE avant la boucle via reduce+regex unique. Passer en parametre a generateOrderNumber pour skip le scan.

### authRateLimitState Map non-bornee sous attaque distribuee
**File** : `server.js:307, 366-377`
**Evidence** : Map keye par IP. Cleanup 5min n'a pas de hard limit. Attaque distribuee maintenant 1 req/15min par IP peut accumuler 100k+ entrees consommant plusieurs MB.
**Impact** : DoS-of-the-DoS-protection. Heap croissance non-bornee.
**Fix** : Hard limit MAX_RATE_LIMIT_ENTRIES=50000. Eviction FIFO des plus anciens 10% si depasse. Log warn a 80%, error a 100%.

### writeDb JSON.stringify(db, null, 2) — 50MB heap spike en mode JSON
**File** : `server.js:1748`
**Evidence** : Pretty-print sur DB 50MB = 50MB+ string temporaire. GC pressure. SQLite path (defaut) evite mais mode JSON legacy vulnerable.
**Impact** : Heap spike sur deploiements JSON.
**Fix** : Retirer `null, 2` (compact JSON). Documenter en CLAUDE.md que JSON mode est legacy/migration-only > 10MB.

### Path traversal latent — archive filename re-expose dans Content-Disposition
**File** : `server.js:2244-2261` (archiveImportFile + downloads)
**Evidence** : `originalName` stocke en DB (l.2261) puis re-emis via `res.download(archive.archivedPath, archive.filename)`. Si attaquant force `Content-Disposition: filename="shell.php.xlsx"`, navigateur peut le re-emettre.
**Impact** : Latent — directory n'est pas servi statique aujourd'hui mais ferait XSS/exec si refactor.
**Fix** : `archivedFilename = ${timestamp}_${type}_archive_${uuid().slice(0,8)}.xlsx` (discard originalName). `res.download(archivedPath, \`archive-${id}.xlsx\`)`. Ne plus stocker originalName en DB pour archives.

### CSRF — Origin check sur req.get('host') spoofable
**File** : `server.js:1215-1245`
**Evidence** : `new URL(origin).host === req.get('host')`. `trust proxy = 1` n'affecte que req.ip, pas Host. Si SWAG mal configure laisse passer X-Forwarded-Host ou attaquant force Host, comparaison reussit.
**Impact** : CSRF possible en cas de mauvaise config proxy.
**Fix** : Allowlist hardcoded `SEREO_ALLOWED_HOSTS=sereo.dockerswag2024.duckdns.org`. Exiger `X-Requested-With: XMLHttpRequest` sur mutations. Upgrader SameSite=Strict.

### XSS via SVG data:URL dans applyBrandImage
**File** : `public/js/app.js:2422-2437`
**Evidence** : `file.type.startsWith('image/')` (l.2373) accepte `image/svg+xml`. `image.src = effectiveSrc` accepte `data:image/svg+xml;base64,...`. SVG avec `<script>` ou `<svg onload>` execute via `<img>` tag selon contexte navigateur.
**Impact** : XSS persistant si data URL stockee en DB (settings appearance) et re-appliquee au rendu.
**Fix** : Rejet client : `if (file.type === 'image/svg+xml' || file.name.endsWith('.svg')) return notify('SVG non autorise')`. Backend : reject `data:image/svg+xml` dans saveAppearance. Whitelist stricte JPEG/PNG/WebP recommandee.

### Recovery suspend backups indefiniment — fenetre de perte post-recovery
**File** : `server.js:1330-1339, 1791-1801`
**Evidence** : Apres recovery, `lastStorageRecovery` flag empeche tout backup futur jusqu'au prochain redemarrage propre. Si container crash 5h apres recovery, toutes mutations entre-temps sont perdues sans backup.
**Impact** : Perte donnees critiques entre recovery et redemarrage.
**Fix** : Differencier modes. Pour `restored_backup` : grace period 5min puis reprendre backups normalement. Pour `fresh_empty` : garder suspension actuelle. Ajouter endpoint `POST /api/backup/now` pour backup force.

### Bucketing import — dates invalides silencieusement fallback a today
**File** : `server.js:1944-1998, 3763, 3831`
**Evidence** : `normalizeDateInput` retourne string vide pour dates invalides. `excelDateToIso()` ne wrap pas l'erreur. Ligne 3831 : `dateCommande = vente.dateCommandeIso || todayIso`. Resultat : 5 lignes Excel avec 5 dates invalides differentes mergent en UNE commande dateCommande=today.
**Impact** : Fusion silencieuse de commandes distinctes, ERP bucketing viole.
**Fix** : Retourner `{ok, value, error}` structuree. Tracker `invalidDateCount` comme `clampedNegativeQtyCount` deja existant (l.4033). Exposer dans response import.

### Promise.all sans catch granulaire — wipe total UI sur 1 endpoint lent
**File** : `public/js/app.js:540-600` (loadData)
**Evidence** : `Promise.all([9 apiFetch])` avec un seul .catch global. Si 1 endpoint sur 9 timeout (30s), tout est wipe : clients=[], orders=[], stock=[]. UX entierement perdue.
**Impact** : UX catastrophique sur slow network ou panne partielle backend.
**Fix** : `Promise.allSettled` ou `.catch` individuel sur chaque fetch avec fallback type-aware (`[]` ou `{}`). Toast "Stock indisponible, prep OK" plutot que wipe.

### Etat global frontend — 17 variables module-level mutables, 100+ mutations eparses
**File** : `public/js/app.js:1-36`
**Evidence** : `let map, clients, orders, stock, stockMovements, ventes, historique, sectors, deliveryRoutes, dashboard, route, activeRoute, currentIndex, activeStopIndex, markers, routeLine, deliverySelection, deliveryFilter, stockFilter, lastImportSummary, recommendFilter, activeThemeId, activeBrandImage, activeColorScheme`. 191 fonctions mutent ces variables sans validation centralisee.
**Impact** : Etat incoherent possible (ex: activeRoute existe mais activeStopIndex out-of-bounds). Pas d'undo/redo, pas de logging mutations, refactor impossible.
**Fix** : Structurer en `AppState = { map, data:{}, route:{}, ui:{}, theme:{} }`. Setters explicites (`setActiveRoute(newRoute)`) avec validation des invariants. Migration phasee.

### Render bonsCommande O(n²) sans memoization
**File** : `public/js/app.js:1648-1659, 2171-2184`
**Evidence** : `Array.from(new Set(...orders.map(o => o.sector).filter(Boolean)))` recalcule sur chaque renderBonsCommande (declenche par search input, status, sector, date). bdcFilterOrders chaine 5 .filter() + .sort(). 500 commandes × 10 keystrokes = 50k iterations par mot tape.
**Impact** : Lag clavier visible > 200 commandes.
**Fix** : Cache `bdcState.cachedSectors` invalide uniquement sur loadData. Memoize bdcFilterOrders par hash des params filtre.

### Event binding heterogene — chercher un listener dans 4 patterns
**File** : `public/js/app.js:317-434` (bindUi)
**Evidence** : (A) delegation document.addEventListener('click') avec closest('[data-*]') pour 36 actions, (B) getElementById().addEventListener pour stockSearch/Filter, (C) querySelectorAll().forEach pour data-tab, (D) form submit direct. Maintenance fragile, 50% de code de binding redondant.
**Impact** : Ajout/modif listener requiert audit de 4 zones. Bugs silencieux sur typo data-action (CSP bloque pas).
**Fix** : 3 listeners centralises : click (data-action/data-tab), change (data-filter-*), submit (forms). Normaliser IDs en data-* attributes.

### apiFetch race — signal aborted avant fetch ignore par fallback
**File** : `public/js/app.js:3407-3424`
**Evidence** : Sur signal externe deja aborte, `addEventListener('abort', ...)` ne se declenche jamais (event passe), fetch part avec signal frais. Timeout externe perdu.
**Impact** : Fuites AbortController, requetes non-interrompues.
**Fix** : `if (options.signal?.aborted) throw new DOMException("Aborted", "AbortError")` AVANT fetch().

### applyTheme/applyColorScheme — saveAppearance() Promise silencieuse
**File** : `public/js/app.js:2321-2339, 2267-2303`
**Evidence** : `applyTheme(themeId, {persist:true})` declenche `saveAppearance()` async sans retour de Promise. Si PATCH echoue, theme applique visuellement mais DB pas synchronisee. Refresh = ancien theme revient (confus).
**Impact** : Desync UI/DB silencieuse.
**Fix** : Separer `applyThemeVisually()` (sync DOM) de `saveThemeToDb()` (async). applyTheme retourne TOUJOURS Promise. Appelant await + .catch.

### action data-* hardcoded — 40+ strings sans enum, typos silencieuses
**File** : `public/js/app.js:370-418, public/index.html:164-854`
**Evidence** : `data-action="start-preparation"` vs `start-prepration` (typo) ne bind pas, aucune erreur. 36 if-chain au lieu de switch enum.
**Impact** : Bugs silencieux lors refactor HTML.
**Fix** : `const ACTION_TYPES = { START_PREP: 'start-preparation', ... }`. switch(action). validateDataActions() au boot qui scan tous [data-action] vs enum.

### Confirmation destructive via window.confirm() — purge orders + reset tournee
**File** : `public/js/app.js:2707-2708, 3172-3173`
**Evidence** : Purge utilise 2 `window.confirm()` consecutifs ("Tape OK pour confirmer"). Reset tournee : `window.confirm("Reinitialiser tous les statuts...")`. Dialogues OS natifs : non navigables Tab, support lecteur ecran variable, message multiline 13 lignes incomprehensible.
**Impact** : Action destructive irreversible sans confirmation accessible. Violation WCAG 2.4.3 + 2.1.1.
**Fix** : Modal reutilisable role="alertdialog" aria-modal="true". Focus initial sur "Annuler". Escape=annuler, Enter=confirmer. Implementer une seule fois, reutiliser dans purge + reset + futures destructions.

### File input focus invisible
**File** : `public/css/style.css:1799-1809`
**Evidence** : `.file-control input::file-selector-button` style custom mais sans `:focus-visible` outline. Le selector global `input:focus-visible` (l.303) ne cascade pas aux pseudo-elements.
**Impact** : Imports Excel non-detectables au clavier. Violation WCAG 2.4.7.
**Fix** : `.file-control input:focus-visible::file-selector-button { outline: 3px solid rgba(244, 122, 90, 0.36); outline-offset: 2px; }`.

### Toast close button focus invisible
**File** : `public/css/style.css:1872-1888`
**Evidence** : `.toast-close:focus-visible { opacity: 1; }` sans outline. Border:0, background:transparent. Sur fond toast sombre, aucun indicateur focus.
**Impact** : Notifications non-fermables au clavier. Violation WCAG 2.4.7.
**Fix** : `.toast-close:focus-visible { outline: 2px solid currentColor; outline-offset: -2px; }`.
