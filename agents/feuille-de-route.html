03 — Séquence

Sept phases, dans cet ordre

L'ordre est contraint : les comptes conditionnent les notifications, le géocodage conditionne la carte, le découpage en modules conditionne l'empaquetage natif. Chaque phase indique ce qu'elle débloque.

Phase 0 1–2 sem.

Assainir les fondations

Rien de visible pour l'utilisateur, tout pour la suite. Le fichier app.js fait 5 653 lignes et le CSS 8 025 — la documentation en annonce respectivement 2 800 et rien. On remet les compteurs à zéro.

  • Jeu d'icônes complet, usages any et maskable séparés, balises iOS
  • Découpage de app.js en modules ES natifs, sans bundler — 5 653 → 4 986 lignes
  • Filet e2e : parcours des 15 onglets, parité des thèmes
  • Mise à jour de CLAUDE.md avec les tailles réelles
  • Découpage du CSS en couches → reporté en phase 4, voir ci-dessous
Débloque Installation sur écran d'accueil Empaquetage natif
Phase 1 2–3 sem.

Comptes et rôles

Passage d'un mot de passe partagé à de vraies identités. C'est le prérequis dur des notifications : sans savoir quel appareil appartient à qui, on ne peut prévenir personne.

  • Table utilisateurs, hachage scrypt via node:crypto — aucune dépendance ajoutée
  • Rôles admin, bureau, préparateur, livreur, avec garde-fou du dernier administrateur
  • Connexion par compte, sans casser l'authentification par variables d'environnement
  • Révocation immédiate : désactiver un compte coupe la session en cours
  • Décision : tout le monde voit tout. La séparation reste écrite et testée, derrière un interrupteur
  • Écran d'administration des comptes, et API correspondante
  • Décision du 16/09 : un seul compte reste utilisé pour l'instant. Les comptes par personne existent et attendent le besoin réel — les notifications de la phase 6
  • Refus côté serveur pour l'administration des comptes
  • Table appareils, pour rattacher les jetons de notification
  • Reprises de la phase 0 : découpage par domaine, fragilité e2e, pré-cache désaligné
Débloque Notifications ciblées Traçabilité des actions
Phase 2 1–2 sem.

Géocodage et entrepôt

La carte se remplit enfin. Le serveur interroge l'API Adresse de l'État — gratuite, sans clé, conçue pour les adresses françaises — et met le résultat en cache dans SQLite. On ne géocode jamais deux fois le même client.

  • Géocodage automatique déclenché à l'import, en tâche de fond
  • Cache en base, hors du cycle de réécriture qui l'aurait effacé à chaque import
  • Seuil de confiance mesuré sur l'API réelle, pas deviné
  • Écran de reprise des adresses ambiguës — après les maquettes, pour ne pas le dessiner deux fois
  • Point de départ — tranché par Tom le 16/09 : pas d'entrepôt fixe. La tournée part de la position GPS du téléphone, ou d'une ville / adresse recherchée
  • Fin de tournée — tranché par Tom le 16/09 : une adresse d'arrivée choisie, ou « Retour au point de départ »
  • Écrans départ / arrivée : livrés en version provisoire dans la PR 96 de Tom (branche partie de main) — à redessiner en phase 3, à recoder en phase 4

Phase 5 3–4 sem.

Cartographie et trafic réel

Aujourd'hui la tournée se calcule par plus proche voisin sur des distances à vol d'oiseau, et se dessine en traits droits. On remplace les trois à la fois.

  • Optimisation par solveur réel, avec fenêtres horaires et capacité du véhicule
  • Distances et durées routières, pas géodésiques
  • Trafic temps réel — heure de départ tranchée par Tom le 16/09 : c'est l'instant où il appuie sur « Démarrer la tournée »
  • Moteur routier : la PR 96 branche le serveur OSRM public — sans garantie de disponibilité, cinquante commandes au plus, pas de trafic. À héberger ou à remplacer avant un usage quotidien
  • Tracé routier sur la carte, à la place des segments droits
  • Clé d'API strictement côté serveur, plafond de quota journalier
Gain attendu 15 à 25 % de kilomètres en moins
Phase 6 3–5 sem.

Applications natives

Capacitor emballe l'application web existante dans un projet Android et un projet iOS. Le code de la SPA est réutilisé tel quel — pas de réécriture, contrairement à un passage par React Native ou Flutter qui repartirait de zéro sur un ERP en production.

  • Notifications push natives sur les deux plateformes
  • Géolocalisation en arrière-plan, pour suivre la tournée écran éteint
  • Windows et macOS restent servis par l'installation web — aucun développement supplémentaire

04 — Reports

Reporté, pas abandonné

Ce qui a été volontairement décalé, ou découvert en cours de route, avec la phase où ça retombe. Rien ne sort de cette liste sans être fait.

Restructuration du CSS en couches

Annoncée en phase 0, décalée. @layer modifie la résolution de spécificité — une règle non‑layerée bat une règle layerée quelle que soit sa spécificité — donc une migration partielle de 8 025 lignes inverserait la cascade par endroits, en premier lieu sur les thèmes. Et ce CSS est réécrit en phase 4 : le restructurer avant, c'est le faire deux fois.

Phase 4e

Découpage de app.js par domaine métier

La phase 0 n'a sorti que les symboles sans couplage à l'état global. Le reste — stock, commandes, préparation, tournée, CRM — exige d'abord un store partagé, ESM interdisant de réassigner un binding importé. app.js pèse encore 4 986 lignes.

Phase 1

Fragilité de la suite e2e

Observée une fois puis non reproduite sur cinq exécutions. La cause de fond est réelle et antérieure : dix workers en parallèle sur un seul serveur et une seule base SQLite, dont un test qui écrit des réglages sans les restaurer. La CI la masque avec deux tentatives.

Phase 1

Pré-cache du service worker désaligné

Le worker pré-cache /js/app.js, mais la page demande /js/app.js?v=…. L'API Cache compare l'URL complète, requête comprise : l'entrée pré-cachée n'est donc jamais servie pour ce fichier. Sans conséquence en usage normal, mais le tout premier chargement hors ligne après installation peut échouer. Vérifié le 28 août : trois entrées sont concernées, pas une — app.js, style.css et le logo, tous demandés avec un ?v=.

Phase 1

Un test invisible en revue

test/corruption.test.js contient un octet nul — l'en-tête « SQLite format 3 » qu'il fabrique se termine ainsi — donc git le classe binaire et n'en montre jamais le diff, ni en PR ni dans git log -p. Un .gitattributes avec *.js diff rétablit la revue sans toucher au test.

Phase 1

Dix-sept fichiers non suivis dans data/

Résidus de sessions d'audit, dont deux Excel d'import et des archives, non couverts par .gitignore — sur un dépôt public. Un git add -A les publierait. À ignorer ou supprimer.

Phase 1

Deux résidus mineurs

formatImportStats reste dans app.js — seule fonction de sa famille à lire l'état global, elle partira avec le domaine stock. Et --body-gradient-stop-mid est déclarée en double dans le bloc sombre : redondance vérifiée inoffensive, à nettoyer au passage.

05 — Arbitrages

Ce qu'il faudra décider, et ce que ça coûte

Trois points engagent de l'argent ou du matériel et n'ont rien de bloquant avant la phase 5. Deux autres, ajoutés le 16 septembre, se règlent avant la phase 4.

Publier sur l'App Store 99 $ / an + un Mac

Compiler une application iOS impose macOS et Xcode — il n'existe aucun contournement. Trois voies : acheter un Mac mini, louer un runner macOS en intégration continue, ou renoncer au store et distribuer en interne. Pour une poignée d'utilisateurs internes, la distribution directe suffit et évite la validation Apple.

Publier sur Google Play 25 $ une fois

Optionnel. Un fichier APK s'installe directement sur les téléphones de l'équipe sans passer par le store, ce qui est parfaitement adapté à un outil interne et supprime le délai de validation à chaque mise à jour.

Optimisation de tournée avec trafic ≈ 0 € au volume actuel

L'API d'optimisation de Google se facture au nombre de livraisons traitées, avec mille unités offertes chaque mois. À dix-huit commandes par jour, l'usage reste sous le seuil gratuit. Le vrai risque n'est pas le prix normal mais une boucle bugguée : un plafond de quota journalier côté console règle la question. Le tarif reste à confirmer sur la grille en vigueur au moment du branchement.

Ordre de fusion des deux branches 0 € · quelques heures

La branche V8 (comptes, géocodage, maquettes — huit commits) et la PR 96 de Tom (abonnements, tournées — un commit) sont parties toutes deux de main et se marchent dessus dans cinq fichiers. Recommandation : livrer d'abord la V8 telle quelle, puis rebaser la PR 96 dessus. L'inverse obligerait à réécrire huit commits pour en épargner un.

Qui fait quoi : Claude Design dessine, Claude Code construit 0 €

Claude Design prend la phase 3 et seulement elle : design system, écrans, prototype cliquable, avec le modèle choisi dans son sélecteur (Fable 5.1 y est disponible, vérifié par Thomas le 16/09 — la doc de lancement disait Opus 4.7). Le serveur, SQLite, les tests, la fusion de la PR 96, la carte et les applications natives se font dans le dépôt, avec Claude Code. L'export de Claude Design vers Claude Code est un point de départ pour la phase 4, pas la phase 4.

06 — Garde-fous

Ce qui ne bouge pas

La refonte touche l'interface et la carte. Elle ne remet pas en cause ce qui marche déjà.

Vanilla, sans bundler Les modules ES natifs donnent la modularité d'un framework sans étape de compilation — donc aucun build à réparer un dimanche soir.
SQLite comme source de vérité Via le module natif de Node. Le schéma s'étend, il ne se remplace pas.
Politique de sécurité stricte Aucun script en ligne, aucun appel externe depuis le navigateur. Tous les appels aux API de cartographie passent par le serveur.
Le cycle de publication Commits conventionnels, versions automatiques, déploiement sur étiquette. Une phase égale une demande de fusion.
Le fonctionnement hors ligne Le cache de l'application est déjà solide : réseau d'abord, repli sur les dernières données connues au bout de trois secondes. On l'étend, on ne le refait pas.
Tout en français Interface, messages, commits. Y compris le nouveau code.
